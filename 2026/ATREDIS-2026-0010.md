## Foresight Sports: GC3 Launch Monitor Multiple Vulnerabilities

## Vendors

* Foresight Sports

## Affected Products

* Foresight Sports GC3
* Firmware Version: 3.3.4.22

## Summary

The fss-control-app service runs as root and is reachable over TCP/9970, USB-HID gadget, and USB-MTP. No authentication is required to access this service.

Atredis Partners identified multiple vulnerabilities that can lead to code execution and memory disclosure. Each vulnerability is documented below.

## Remediation/Mitigation

Upgrade to version 3.3.6.30 or later.

This issue was found by Tom Steele of Atredis Partners.

## Technical Details

### Improper Limitation of a Pathname to a Restricted Directory ('Path Traversal')

The file-transfer message handler can be reached from the class-`0x200` dispatcher via sub-command `0x14`. The message body is:

```text
[fname_len:1][filename][filedata]
```

The following decompiled and documented function is used to open and write the file:

```c
int File_WriteToFlash(char *filename, int openFlags, char useHiddenDir) {
    const char *base = (useHiddenDir == 0) ? "/mnt/flash" : "/mnt/flash_hidden";
    __snprintf_chk(path, 0x1000, 1, 0x1000, "%s/%s", base, filename);
    fd = open(path, openFlags, 0644);
    ...
}
```

The FSS file-transfer message `0x0214` allows an attacker with access to the control service over TCP or USB to write caller-supplied data to a caller-supplied filename. The filename is concatenated with a base directory before the file is written. Because no path sanitization is applied, an attacker can supply path traversal sequences such as `../` to create or overwrite files elsewhere on the filesystem.

This can be leveraged to gain remote access to the device as the root user by overwriting `/home/root/.ssh/authorized_keys` with an attacker-controlled SSH public key.

As shown above, the filename is appended to the base path without sanitization. A filename such as:

```text
../../home/root/.ssh/authorized_keys
```

results in the path:

```text
/mnt/flash/../../home/root/.ssh/authorized_keys
```

which resolves to:

```text
/home/root/.ssh/authorized_keys
```

This truncates and replaces root's authorized keys file. The SSH configuration permits public-key-based root login using:

```text
PermitRootLogin prohibit-password
AuthorizedKeysFile .ssh/authorized_keys
```

As a result, SSH access succeeds with:

```sh
ssh -i <key> root@<device>
```

This issue may also allow attackers to create startup scripts, overwrite licensing files, or modify other security-sensitive files.

### Improper Neutralization of Directives in Statically Saved Code ('Static Code Injection')

The FSS message `0x0234` allows an attacker with access to the control service over TCP or USB to set the device's Wi-Fi SSID and PSK. These values are written verbatim into the root `wpa_supplicant` configuration file at:

```text
/mnt/flash_hidden/wifi.conf
```

Because quote and newline characters are not neutralized, an attacker can break out of the `psk="..."` field and inject arbitrary global directives. Some `wpa_supplicant` directives support loading shared objects, including `opensc_engine_path`. Combined with USB-MTP access to the filesystem, this can be used to achieve code execution.

The handler for `0x0234` passes the attacker-supplied SSID and PSK to the routine that saves the Wi-Fi configuration. That routine templates the file using the following unsanitized format string:

```c
// writes /mnt/flash_hidden/wifi.conf


__snprintf_chk(buf, 0x100, 1, 0x100,
   "country=%s\nctrl_interface=DIR=/var/run/wpa_supplicant GROUP=0\nupdate_config=1\n\n"
   "network={\n  ssid=\"%s\"\n  psk=\"%s\"\n}\n\n", country, ssid, psk);
```

Only the SSID length is checked. Neither `"` nor `\n` is filtered from the SSID or PSK. A PSK value such as the following can be supplied:

```text
AAAAAAAA"
}
opensc_engine_path=/mnt/flash/a.so
network={
#
```

This will render as a valid configuration with a self-contained global directive:

```text
network={
  ssid="x"
  psk="AAAAAAAA"
}
opensc_engine_path=/mnt/flash/a.so
network={
#"
}
```

The USB-MTP interface can be used to write a shared object to `/mnt/flash`. On the next `wpa_supplicant` start, `opensc_engine_path` is resolved through OpenSSL's dynamic ENGINE loader, which calls `dlopen()` on the supplied path. The shared object's constructor runs as root before any engine symbols are checked, so the file does not need to be a valid OpenSSL engine.

Atredis Partners validated this finding by creating, compiling, and uploading a shared object that overwrote the root user's SSH `authorized_keys` file.

### Use of Uninitialized Resource

An attacker can cause the FSS control service to send process memory over TCP or USB. When handling certain error conditions, the `0x0234` message handler writes only a short reply into a response buffer but sends a fixed-size response length of 263 bytes. As a result, uninitialized memory is transmitted after the intended error message.

An attacker can use this memory disclosure to inspect sensitive application state and potentially bypass exploit mitigations such as ASLR.

A single plaintext `0x0234` request with an empty body produces a 263-byte reply. Only the first approximately 57 bytes contain the intended response: a 6-byte header, a status byte, and the NUL-terminated string:

```text
FSS_REQ2_CONFIGURE_COMMS message MUST be encrypted
```

The remaining bytes contain uninitialized process memory. The included proof-of-concept, `fss_memleak_poc.py`, sends the request and dumps the reply:


Everything after the string, beginning at offset `0x39`, is uninitialized. The leaked data changes between requests and across reboots and contains 8-byte values that appear to be live addresses. The bytes at `+0x70` represent a socket address and port:

```text
84 01 a8 c0 f2 26
```

```text
192.168.1.132:9970
```

The root cause is a length mismatch. The handler writes only the short status string into its response buffer, but then uses a hard-coded response length that is much larger. The shared send routine transmits the specified number of bytes from the provided buffer, including bytes past the initialized portion.

Relevant decompiled logic:

```c
__snprintf_chk(buf, 0x100, ..., "FSS_REQ2_CONFIGURE_COMMS message MUST be encrypted");
...
resp_len  = 0x107;      // 263: fixed constant, not the number of bytes written
resp_data = buf;        // only the leading ~57 bytes of buf were written
send_reply(...);        // transmits resp_len bytes starting at resp_data
```

Because the response length is hard-coded rather than derived from the number of bytes actually written, the send routine reads past the initialized portion of the buffer and transmits unwritten memory to the client.

The send routine is shared and transmits a caller-specified length from a caller-specified buffer for every message type. As a result, this issue is unlikely to be unique to `0x0234`. Any handler that reports a length larger than the amount of data it actually writes may leak memory in the same way. The message layer should be reviewed for this pattern.

The `0x0234` handler can be reached through both plaintext and encrypted requests. The plaintext path described above is the simplest trigger. The encrypted path reaches the same fixed-length send behavior through size and interface-validation error replies, but requires the ECDH handshake first.

### Stack-based Buffer Overflow

The USB-HID receive path of the control service copies received bytes into a fixed-size stack buffer without a bounds check. An attacker with USB access can stream more bytes than the buffer can hold and overwrite the saved return address, causing the control service to crash.

Using the memory disclosure vulnerability described above, it is possible to bypass exploit mitigations and craft an exploit that achieves command execution as the root user, resulting in full device compromise.

The receive routine reads HID bytes one at a time. Until it sees the `0x3F` (`?`) start byte, it stores each received byte into a fixed 64-byte stack buffer at an ever-incrementing index. There is no check to ensure the index remains within the bounds of the buffer. As a result, a stream of more than 64 non-`0x3F` bytes writes past the end of the buffer and overwrites the rest of the stack frame, including the saved return address.

```c
// USB-HID receive path (decompiled, condensed)


char buf[64];                             // fixed-size stack scratch buffer
int  i = 0;
while ((b = read_hid_byte()) != '?') {    // 0x3F = start byte
    buf[i++] = b;                         // no check that i < sizeof(buf)
}
```

Atredis Partners achieved reliable code execution with a proof-of-concept. Exploit mitigations were ineffective on the tested device for the following reasons:

- The buffer is a variable-length array allocated via `alloca`
- On the GCC AArch64 toolchain used for this firmware, the stack canary is not placed between this type of buffer and the saved return address, likely due to CVE-2023-4039.
- The ASLR/PIE base and canary value can be recovered using the memory-disclosure vulnerability described above.
- PAC and BTI are not enforced on the tested CPU.
