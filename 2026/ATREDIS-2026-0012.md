# Steam - Multiple Vulnerabilities

## Vendors

* Valve

## Affected Products

Steam version <= 1773426488 (client build date 3/12/2026)
RCEs patched July 2026.

## Summary

Atredis identified multiple flaws in Valve's Steam platform that can be exploited by local attackers to obtain privilege escalation. In other cases, remote attackers with the password to a Steam account can obtain code execution on any device in which that user is logged in. 

## Remediation/Mitigation

Update to Steam to 1792618285 or later.

## Credit

These issues were found by Bryan Alexander of Atredis Partners.

### Local Privilege Escalation via IClientInstallUtils
One function within Steam's client interface, `IClientInstallUtils::RunInstallScript`, is responsible for parsing and activating Valve Data Files (VDF) for games and software. The function's prototype is as follows:

```
IClientInstallUtils::RunInstallScript(String path_to_vdf, int appId, bool uninstall);
```

These undocumented file types are used by Steam to configure and install games and their dependencies. An example of one is as follows (CS:GO):

```
"installscript"
{
	"utf8_registry_strings"		"1"
	"registry"
	{
		"hkey_local_machine\\software\\valve\\cs2"
		{
			"string"
			{
				"installpath"		"%INSTALLDIR%"
			}
		}
	}
}
"kvsignatures"
{
	"installscript"		"8a80c9a3a8ab75b8f133929a0e89978531d7e49a074d6a305ca47097c268f18c6522ccca65138f831f327afcbcaea43cee8e6861f353c597c86feab0c2fd6562bd3ab6c72ad34e861e421315af3054c76933c9d882d9476bde6098152a5bedfcd2103591a91b27bb95c8c1d4519684542790e6cbd93144e8a5b77ec8298f80cd"
}
```

When processed by `SteamService` this will use the `IRegistryInterface` to install the `installpath` key under the configured HKLM path. Because this is a privileged operation, however, `SteamService` will first authenticate the provided VDF. This is done using the `kvsignatures` section which includes an RSA signed blob over the contents of the VDF. These are built and signed by Valve and therefore not something we can forge ourselves.

VDF files additionally support the `Run Process` directive as seen in the following example (Hotline Miami):

```
"Run Process"
{
	"Visual C++ 2010 SP1 Redistributable Package (x86)"
	{
		"process 1"		"%INSTALLDIR%\\redist\\vcredist_x86.exe"
		"command 1"		"/q:a"
		"description"		"Visual C++ 2010 SP1 Redistributable Package (x86)"
		"NoCleanUp"		"1"
		"IgnoreExitCode"		"1"
	}
}
```

This is used to install dependencies (such as DirectX redistrib packages or anti-cheat software). In order to prevent arbitrary executables from being run as SYSTEM, any target processes in VDFs must be added to an internal runtime allowlist.

The `IClientInstallUtils` interface exposes `AddInstallScriptToWhitelist` which is used to allowlist process executables (with their fully resolved paths) that a VDF can use in its `Run Process` or `Run Process On Uninstall` directives. In order for this to be achieved, however, the requesting VDF must be signed and authenticated. Only once the VDF is authenticated will the target executable be allowlisted. There is no additional verification of the target binaries.

The allowlist is a linked list and exists only in-memory at runtime. Once the Steam service restarts the allowlist is purged and must be reinitialized by game install or uninstall operations. We can dump the list at runtime using Windbg:

```
0:001> r $t1 = dwo(steamservice+0x3630C0)
0:001> .printf "0: %ma\n", dwo(@$t1 + 0x10)
Node 0: D:\Steam\steamapps\common\Steamworks Shared\_CommonRedist\OpenAL\2.0.7.0\oalinst.exe
0:001> .printf "1: %ma\n", dwo(@$t1 + 0x28)
Node 1: D:\Steam\steamapps\common\Steamworks Shared\_CommonRedist\DotNet\3.5\dotnetfx35.exe
```

My installation of Steam is at `D:\` and we see two executables that've been allowlisted as the result of a game installation. Note that `%INSTALLDIR%` was fully resolved and allowlisted with its full path; a path that unprivileged users have write access to by default.

The previously mentioned `AddInstallScriptToWhitelist` is more interesting, however, and useful in this chain. Its prototype is:

```
IClientInstallUtils::RunInstallScript(String path_to_vdf, String installDir);
```

The `path_to_vdf` is a VDF with a valid signature block and the `installDir` is what resolves `%INSTALLDIR%`. Using this we can take a pre-existing VDF with a relative path and set `installDir` to `%APPDATA%` or something similar. Now the target binary with a root `%APPDATA%` is executable.

Because there is no additional verification of target binaries, because the allowlist persists after the VDF is actioned, and because arbitrary VDFs can be submitted to the service for processing, we can abuse this configuration to execute arbitrary code. By allowlisting a user-controllable path with a pre-existing VDF and creating a custom VDF with a `Run Process` directive we can coerce the system service into executing arbitrary system executables as SYSTEM.

First, we need to identify an authenticated VDF. If you have Steam installed with a game or two, you'll have one. I chose Hotline Miami because it includes a signature block and a target process:

```
"InstallScript"
{
	"Run Process"
	{

		{
			"process 1"		"%INSTALLDIR%\\redist\\vcredist_x86.exe"
			"command 1"		"/q:a"
			"description"		"Visual C++ 2010 SP1 Redistributable Package (x86)"
			"NoCleanUp"		"1"
			"IgnoreExitCode"		"1"
		}
	}

"kvsignatures"
{
	"InstallScript"		"54ec3608942bc3b574c27b8224d6dffa4d2377c21f034187022529dc7820841b325955d9cee51ffe6ebf6b00e3db332d225e49aab628bcebc52449f5f1f8912c27d90fe0d177040fdefadbfcb2665b9bb065fe50293db88cc0159fc670eac253a51f9afffe593e5b3fc81e3d25412251934bbb2e8a9710d194278e3a82ca228e"

```

Second we submit this to `AddInstallScriptToWhitelist` to add a custom path and the binary to the allowlist (from within the `steam.exe` process):

```

```

In this case `installscript.vdf` is the Hotline Miami VDF listed above. We then replace `redist\vcredist_x86.exe` with `cmd.exe`.

Third we generate a VDF to execute our target payload:

```

      {
```

We're now ready to send a `RunInstallScript` request. To do this we need to connect to the IPC endpoint and, to accomplish that, we need to inject into a running and connected `steam.exe` process. A full proof of concept is provided at the end of this advisory. Finally, we inject the DLl into the running process and observe execution (procmon execution event):


In summary, the following steps are performed to escalate to SYSTEM:

1. Create a folder at `%TMP%\redist`
2. Copy the authenticated VDF described above into this path
3. Copy `cmd.exe` into this path and rename it `vcredist_x86.exe`
4. Compile the DLL and inject it into `steam.exe` , which:
   1. Resolves vtable pointers to `RunInstallScript` and `AddInstallScriptToWhitelist`
   2. Calls `AddInstallScriptToWhitelist` with our authenticated VDF and `%TMP%` as its `installDir`
   3. Write our unauthenticated VDF to disk which executes our now-cmd.exe `Run Process` directive and arbitrary command line arguments
   4. Invoke `RunInstallScript`

### Local Privilege Escalation via IClientModuleManager
One function within Steam's client interface, `IClientModuleManager::CallFunctionAsync`, appears to invoke `steamservice.exe` to dynamically run an exported function from a DLL. While the true purpose of the function is unclear it seems to be related to legacy support due to path naming. The `IClientModuleManager::Dispatch` function parses the interface request and checks the CRC:

```c

      {
```

After parsing six parameters off the IPC request, the item is queued for asynchronous execution `QueueWorkItem`). This is eventually picked up by the `ModuleManager::WorkItemExecutor` on a separate thread and takes one of two paths:

```c

    v7 = ModuleManager_CallFunction_ChildProcess(v6, v11, v5, v12, v13, v14, v15, v4, v3, v16, v17);

```


`LookupModuleById` takes a CRC32 (provided by the IPC request) and performs a binary lookup to see if the module is loaded. If not, it bails, but if found, it continues.

In short, the function then validates the RSA signature on the DLL to authenticate it has a valid digital signature from Valve. If the module is authenticated, it then reflectively loads the DLL into memory using the standard `VirtualAlloc` + relocation strategy.

The second path previously noted, `ModuleManager_CallFunction_ChildProcess` , is more interesting. This path goes through a similar `LookupModuleById` process and, when found, writes the DLL to disk at `%SteamInstallDir%/legacycompat/servicecall_%u.dll` where `%u` is the CRC32 of the module. Once written, two more files are created to handle io:

```c

sub_1007C150(v47, "%s/legacycompat/servicecall_%u.out", fPath, v21);
```

Next a command line string is composed:

```c
sub_1007C150(v43, "%s/legacycompat/steamservice.exe /runfunc %u %u %u %u", fPath, v37, v38, v21, v39);
```

Again the path is pulled from `%SteamInstallDir%`. Finally, the following is called:

```

    {
      WaitForSingleObject(hHandle.hProcess, 0x4E20u);
      GetExitCodeProcess(hHandle.hProcess, &ExitCode);
      CloseHandle(hHandle.hProcess);
      CloseHandle(hHandle.hThread);
    }
```

`doCreateProcess` calls `CreateProcessW` with the composed command line and the in/out files removed. There is no validation of the module written to disk nor of `steamservice.exe` executed from the user-writable path.

Two questions remain: how do we load a DLL into this internal module store and how do we set the flag toggling which loading function to call? The first can be accomplished via a second IPC function exposed on the `IClientModuleManager` interface: `LoadModule`. This is a relatively trivial function that has the following prototype:

```
IClientModuleManager::LoadModule(lpvoid this, uint module_id, lpvoid dll_data, uint dll_size);
```

As long as the computed CRC32 matches what it internally calculates, the module and its contents will be stored in the list.

Finally, the toggle flag also appears to be exposed directly via the IPC interface. The `CallFunctionAsync` function has the following prototype:

```
IClientModuleManager::CallFunctionAsync(lpvoid this, uint module_crc, uint flags, uint A, unint B, unint C, uint D, lpvoid input_data, uint input_data_size, uint output_size);
```

The `flags` parameter directly sets the internal `flags` variable used to control how to load and execute the module.

In summary, the following steps are performed to escalate to SYSTEM:

1. Create `legacycompat` folder in `%SteamInstallDir%`
2. Write arbitrary executable into this folder named `steamservice.exe`
3. Connect to IPC from within `steam.exe` and send an arbitrary DLL via `IClientModuleManager::LoadModule`
4. Call `IClientModuleManager::CallFunctionAsync` with `flags` bit 3 set to bypass RSA signature verifications

### Local Privilege Escalation via Secure Desktop Capture
One interface in the Steam client interface, `IClientSecureDesktop`, is used to provide support for a variety of Steam features, including Big Picture mode, Steam Remote Play, Steam Link, and other features that require providing system input from contexts in which a keyboard/mouse may not be available. For example, when a remote client streams the host machine, it forwards keyboard/mouse input over the network. If a prompt appears on the host during the stream, such as a UAC prompt in the secure desktop, the remote user would be stuck with an unresponsive screen.

In order to facilitate managing these pop-ups, Valve built `secure_desktop_capture`. This is launched by `SteamService.exe` when `IClientSecureDesktop::BStartStreaming` is called:

```cpp
if ( DuplicateTokenEx(TokenHandle, 0x2000000u, &TokenAttributes, SecurityIdentification, TokenPrimary, &phNewToken) )
    {
      v19 = L"winsta0\\winlogon";
      if ( !a6 )
        v19 = L"winsta0\\default";
      v20 = TokenInformation == -1;
      lpStartupInfo->lpDesktop = v19;
      if ( !v20 )
        SetTokenInformation(phNewToken, TokenSessionId, &TokenInformation, 4u);
      v21 = 48;
      if ( !a5 )
        v21 = 0x8000020;
      v22 = v21 | 0x400;
      if ( !lpEnvironment )
        v22 = v21;
      v18 = CreateProcessAsUserW(
              phNewToken,
              0,
              lpCommandLine,
              &TokenAttributes,
              &TokenAttributes,
              0,
              v22,
              lpEnvironment,
              0,
              lpStartupInfo,
              lpProcessInformation);
    }
```

This launches `secure_desktop_capture.exe` as SYSTEM in `winsta0\winlogon` , which is the secure desktop. Once the target is running it sets up two shared memory regions: an output frame buffer (`Global\SecureDesktop_MovieStream_mem-IPCWrapper` ) used to pass secure desktop frame content to a client, and an input buffer (`Global\SecureDesktopInput_mem-IPCWrapper`) to forward keyboard and mouse controls into the secure desktop (via `SendInput`). Both of these regions are created with the same SID allowing `GENERIC_ALL` access to: SYSTEM, Administrators, and the user that owns `steam.exe` (looked up via HKCU). This means any desktop user can send inputs to the secure desktop and read framebuffer contents.

Note that the input buffer does contain an RSA public key, written in by the `secure_desktop_capture` process on initialization, and encryption is supported, but it is entirely client controlled. Simply writing `flag=0` into your input struct will skip encryption per-slot.

Finally, for inputs to be passed from the user session into the secure desktop, a registry-controlled gate must be enabled. On first launch, `secure_desktop_capture` will check a registry key ( `HKLM\Software\Valve\SteamSecureDesktop\` ) to determine both if the input has been enabled (`InputEnabled`) and if the authorization has expired (90 days). If the input has not been enabled, a message box prompt is displayed to the user. Once accepted, `InputEnabled` is set to 1 and the timestamp is updated. For the next 90 days, all input to the secure desktop input buffer is transparently forwarded to the secure desktop session.

The format of the input channel is relatively straight forward. It's a 128-slot ring buffer, each slot totaling 173 bytes:

```
+0x0000  control header
+0x0014  RSA-1024 PublicKey
+0x0414  write counter
+0x0418  read counter
+0x041C  slot[0]
+0x04C9  slot[1]
...
+ slot[N] @ 0x041C + 173*N for N in 0..127
```

Slots have the following structure:

```
+0 flag  (0 = plaintext, !=0 = encrypted)
+1..40   plaintext INPUT struct (Windows tagINPUT)
+41..44  encrypted_size (set by sender for encrypted-path)
+45..172 RSA ciphertext (up to 128 bytes; decrypts to 44-byte payload)
```

Once a slot has been written to the client updates the write counter and `secure_desktop_capture` will process and transmit the input:

```cpp
while ( *a1 )
{
LABEL_29:
      if ( a1[1] )
        SendInput(v3, &pInputs, 40);
      result = CSecureDesktopInput_fetch_next((__int64)(a1 + 600), (__int64)&pInputs, 2);
      v3 = result;
      if ( !(_DWORD)result )
        return result;
}
```

This allows unprivileged users to send arbitrary keyboard and mouse events to the secure desktop. Overall, the architecture breaks the isolation boundary enforced by Windows in the secure desktop environment by providing an event pump between the two spaces.

In order to exploit this, an attacker can drop an executable on the machine with an application manifest specifying `requireAdministrator` or reuse an existing executable on disk (`msconfig`). An attacker then spawns the process and spams `VK_Y` (or the Y key, which force focuses on the Yes for the UAC prompt) into the input buffer. In testing this has not produced any visual notifications of escalation and occurs immediately.

In summary, the following steps are performed to escalate to SYSTEM:

1. Verify consent cache timestamp
2. Connect to IPC from within `steam.exe` and send the `BStartStreaming` request
3. ShellExecute an executable with `requireAdministrator`
4. Spam `VK_Y` into input buffer

### Local Privilege Escalation via IClientInstallUtils Driver Installation
One function in the Steam client interface, `IClientInstallUtils:InstallVrLinkDongleDriver`, is used to install the wireless driver for the Steam Frame, a common Realtek driver used to stream to the headset. This function accepts a single path parameter (example prototype), expected to point to the directory containing the dongle driver:

```cpp
typedef unsigned char (*fn_install_vrlink)(void* thisptr, const char* path);
```

This function first builds an architecture-specific path and checks for the existence of `netrtwlanuval.inf`:

```cpp
doFormatString(
        a1: (int)&v18,
        a2: (int)"%s\\drivers\\%s\\%s\\%s.inf",
        v6,
        (const char *)wWindowsBuild[2 * v3],
        wArch,
        dwNetRtwInf);
```

If not found, the function falls back to a flat path:

```cpp
doFormatString(a1: (int)&v18, a2: (int)"%s\\%s.inf", wFullPath, dwNetRtwInf);
```

In the flat path case, the path would resolve to `<request provided path>\netrtwlanuva.inf`.

The first thing  `InstallVrLinkDongleDriver` then does is call `WinVerifyTrust` on the catalog file found in the driver path. It does this through the `WINTRUST_ACTION_GENERIC_VERIFY_V2` action ID:

```
LastError = WinVerifyTrust(hwnd: nullptr, pgActionID: &pgActionIdGuid, pWVTData: v37); 
```

This validates the authenticode signature on the catalog file. If validated, the catalog is opened and enumerated to identify authenticated files. With this list of files, the requested directory is then enumerated and its files are hashed (`CryptCATAdminCalcHashFromFileHandle`) to identify matched catalog members. If there's at least one, the function returns successfully.

At this point, the function then begins assembling the command line string for installing the driver. It uses `pnputil`, a common Windows driver tool for plug and play drivers, and executes an install operation using a token from the winlogon process, resulting in the following:

```powershell
C:\WINDOWS\Sysnative\pnputil.exe /add-driver C:\Users\bja\AppData\Local\Temp\steam_stage\netrtwlanuval.inf /install
```

At no point in this process does the function attempt to validate that the requested setup information file is for the expected driver. Furthermore, even if the function performed this check, the process is vulnerable to TOCTOU as the execution occurs after validation and handle release. An attacker could oplock the `inf` and swap it out between validation and `pnputil` execution. 

Leveraging this, an attacker could copy a vulnerable driver onto the victim machine and  install it, exposing the system to further attack and an escalation of privileges.

In summary, the following steps are performed to escalate to SYSTEM:

1. Copy a vulnerable driver package onto the victim machine 
2. Rename the package's setup information file to `netrtwlanuval.inf`
3. Invoke `IClientInstallUtils:InstallVrLinkDongleDriver` with the staging directory path

### Remote Code Execution via RecvMsgAppStatus EMsg
A single account can login to Steam from multiple locations and play games. In order to synchronize state between the various instances, Steam leverages Valve's Connection Manager (CM) infrastructure and a set of internal `SteamToSteamPacket` objects. These are available without pairing (via Remote Play) or otherwise granting permissions beyond an initial login.

Each authenticated instance forms a `CRemoteClient` connection to every other instance. Messages are crafted as `CNetPacket`'s with the following structure:

```
+0x00  uint32  EMsg | 0x80000000
+0x04  uint32  header_size
+0x08  CMsgProtoBufHeader
+...   protobuf message body
```

`EMsg` is the message type and consists of approximately 40 different handlers available at different times of the `CRemoteClient` lifecycle. This packet is then encrypted with a per-session shared key, wrapped into an outer `CRemoteClient::SteamToSteam::Notification` envelope:

```
message CMsgRemoteClientSteamToSteam {
    // AES-encrypted inner CNetPacket  
    optional bytes  payload          = 1; 
    optional uint64 steamid_source   = 2;
    optional uint64 client_id_source = 3;
    optional uint64 client_id_dest   = 4;
    optional uint32 secret           = 5;  // routing/secret token
}
```

In order to serialize and send arbitrary packets to remote clients, we can inject into the `steam.exe` process and walk the `CRemoteClientManager` object which maintains an in-memory map of all available and authenticated `CRemoteClient` objects. Through some runtime hooks and gentle massaging of the object we can leverage existing transmission and encryption functionality of an active Steam process to target `EMsg` handlers on any remote authenticated session. A full description of this process is not included here for brevity.

`EMsg` 9502 (`RecvMsgAppStatus`) reports per-app installation and update status to peers, and has the following descriptor:

```protobuf
message CMsgRemoteClientAppStatus {
  repeated AppStatus status_updates = 1;

  message AppStatus {
    optional uint32         app_id              = 1;
    optional uint32         app_install_state   = 2;
    optional AppUpdateInfo  update_info         = 3;
    optional ShortcutInfo   shortcut_info       = 4;
    optional bool           vr_not_required     = 5 [default = true];
    optional bool           shader_update_available  = 6;
    optional bool           workshop_update_avilable = 7;
    optional bool           download_complete   = 8;
    optional AppCloudStatus cloud_status        = 9;
  }

 message AppUpdateInfo {
  // several scalar progress fields ...
  repeated AppStageProgress stage_progress = 13;
}

message AppStageProgress {                         
  optional uint64  field1 = 1;
  optional uint64  field2 = 2;
  optional uint32  field3 = 3;
  optional fixed32 field4 = 4;
}
```

When a peer receives a `CMsgRemoteClientAppStatus` message, for each `AppStatus` whose `app_install_state` is present, it invokes a processor that copies that record's `update_info` submessage into a fixed stack array.  Annotated loop:

```
// bound = stage_progress.size(); 
for ( i = 0; i < *(int *)(update_info + 32); ++i )
{
    // &stage_progress[i] (AppStageProgress*)
    elem = *(QWORD *)(*(QWORD *)(update_info + 40) + 8*i + 8);
    *(QWORD *)(dst + 80  + 24*i) = *(QWORD *)(elem + 24);
    *(QWORD *)(dst + 88  + 24*i) = *(QWORD *)(elem + 32);
    *(DWORD *)(dst + 96  + 24*i) = *(DWORD *)(elem + 40);
    *(DWORD *)(dst + 100 + 24*i) = *(DWORD *)(elem + 44);
}
```

The fixed `stage_progress` array is a fixed 7-slot array, written one 24-byte record at a time. By sending a message with an `AppUpdateInfo` that carries more than 7 `stage_progress` entries, we can overflow the array. Because the fields are copied from the message onto the stack, we have significant control over what's written. The following message results in significant register control, including RIP:


### Remote Code Execution via RecvMsgDownloadScheduleChanged EMsg
A single account can login to Steam from multiple locations and play games. In order to synchronize state between the various instances, Steam leverages Valve's Connection Manager (CM) infrastructure and a set of internal `SteamToSteamPacket` objects. These are available without pairing (via Remote Play) or otherwise granting permissions beyond an initial login.

Each authenticated instance forms a `CRemoteClient` connection to every other instance. Messages are crafted as `CNetPacket`'s with the following structure:

```
+0x00  uint32  EMsg | 0x80000000
+0x04  uint32  header_size
+0x08  CMsgProtoBufHeader
+...   protobuf message body
```

`EMsg` is the message type and consists of approximately 40 different handlers available at different times of the `CRemoteClient` lifecycle. This packet is then encrypted with a per-session shared key, wrapped into an outer `CRemoteClient::SteamToSteam::Notification` envelope:

```
message CMsgRemoteClientSteamToSteam {
    // AES-encrypted inner CNetPacket  
    optional bytes  payload          = 1; 
    optional uint64 steamid_source   = 2;
    optional uint64 client_id_source = 3;
    optional uint64 client_id_dest   = 4;
    optional uint32 secret           = 5;  // routing/secret token
}
```

In order to serialize and send arbitrary packets to remote clients, we can inject into the `steam.exe` process and walk the `CRemoteClientManager` object which maintains an in-memory map of all available and authenticated `CRemoteClient` objects. Through some runtime hooks and gentle massaging of the object we can leverage existing transmission and encryption functionality of an active Steam process to target `EMsg` handlers on any remote authenticated session. A full description of this process is not included here for brevity.

`EMsg` 9526 (`RecvMsgDownloadScheduleChanged`) is a small status message Steam typically sends when a host's download schedule changes. It's protobuf descriptor is:

```
message CMsgRemoteClientDownloadScheduleChanged {
  optional bool   download_enabled    = 1;
  optional uint32 start_index         = 2;
  optional bool   final_message       = 3;
  optional uint32 num_apps_scheduled  = 4;
  repeated uint32 apps_scheduled      = 5;
}
```

After some preprocessing and parsing of the body, the dispatcher builds an event record on the stack and copies the repeated `apps_scheduled` entries into a list for broadcasting to in-process subscribers. The relevant portion of the function:

```c
v85 = client_id; 
LOBYTE(v86) = *(BYTE  *)(v77 + 44); // final msg
HIDWORD(v86) = *(DWORD *)(v77 + 40); // num_apps_scheduled
...

for ( i = sub_138BCEB70(v77 + 24); // end = data + 4*size
      v34 != (int *)i;
      *((DWORD *)&v88 + v37) = v36 ) // write
{
    v36 = *v34++;   // value = apps_scheduled[k]
    v37 = v33++;    // update idx
}
// transmit events
sub_1389675B0(qword_1397C2D08, 0, 1100059, &v85, 152, 1, 0);  
```

The loop is bounded by `begin != end` over a write on a fixed offset record (152 bytes). Because the size is controlled by the inbound message and there is no bounds checking, a `CMsgRemoteClientDownloadScheduleChanged` with more than 200 elements will overflow the return pointer on the stack. The following loop builds our overflow body:


In summary:

1. An attacker obtains the credentials for a Steam account (phishing, guessing, purchasing online, etc.) and logs in
2. The victim is logged into Steam on another machine and has access to the internet
3. An attacker injects a DLL into their own `steam.exe` process that:
   1. Walks all available client connections
   2. Forge a `CMsgRemoteClientDownloadScheduleChanged` with an excessive number of `apps_scheduled`
   3. Transmit the forged packet, after encryption, to the remote client
